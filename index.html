Integrasi IronSKY ke SIEM — Realtime via Callback SDK

Panduan menangkap event keamanan dari callback SDK IronSKY di dalam aplikasi, lalu meneruskannya ke SIEM Anda seketika (realtime) melalui sebuah collector. Beginner-friendly, lengkap dengan contoh per-framework.

Metode: SDK callback (push) Sifat: realtime Perlu ubah app: ya (beberapa baris) Contoh SIEM: Wazuh

Ringkasan

Metode ini memanfaatkan fakta bahwa SDK IronSKY sudah memanggil callback setiap kali mendeteksi ancaman di perangkat (root, Frida, emulator, MITM, keylogger, dll). Alih-alih menunggu file harian di S3, aplikasi menangkap event itu saat terjadi dan mengirimkannya ke SIEM Anda dalam hitungan detik.

Karena aplikasi mobile tidak boleh memegang kredensial SIEM, event tidak dikirim langsung ke SIEM, melainkan ke sebuah collector (endpoint HTTPS milik Anda) yang lalu meneruskannya ke SIEM.

Untuk Pemula

Callback = fungsi yang "dipanggil balik" oleh SDK saat suatu kejadian muncul. Anda mendaftarkan fungsi Anda, lalu SDK menjalankannya tiap ada event, sambil menyerahkan datanya.

Collector = program kecil/endpoint milik Anda yang menerima data dari aplikasi lalu meneruskannya ke SIEM. Ia menjadi "perantara" agar rahasia SIEM tidak bocor ke aplikasi.

Sudah punya panduan S3?

Ini metode kedua, pelengkap dari panduan integrasi via S3 (batch). Boleh dipakai bersamaan: callback untuk realtime, S3 untuk cadangan/histori.

Tiga bagian: (1) aplikasi menangkap event dari callback, (2) mengirimnya ke collector milik Anda, (3) collector menormalkan & menyuapkan ke SIEM (persis seperti sisi SIEM pada metode S3).

Jangan kirim langsung dari app ke SIEM

Aplikasi mobile bisa dibongkar (reverse-engineer). Jika token/endpoint SIEM ditaruh di app, itu bisa dicuri dan dipakai menyuntik log palsu. Selalu lewat collector yang punya autentikasi sendiri. Lihat bagian Keamanan.

Prasyarat SDK

SDK IronSKY sudah harus terpasang & ter-inisialisasi di aplikasi. Kalau belum, ikuti dulu panduan integrasi SDK IronSKY. Urutan pemanggilan yang benar:

urutan wajib (Android)
1. registerService(...) untuk RISKEVENT   ← daftarkan callback DULU
2. registerService(...) untuk DEVINFO
3. setUserId(...)
4. initAppsecEverisk(context, KEY)         ← init PALING AKHIR
Jebakan urutan (khususnya React Native)

registerService harus dipanggil sebelum initAppsecEverisk. Jika dibalik, callback tidak akan pernah terpanggil (callbacks:0) dan tidak ada event yang bisa Anda kirim ke SIEM.

Callback RISKEVENT

Event risiko dikirim SDK lewat registerService(callback, Type.RISKEVENT, 0.5). Callback menerima sebuah objek JSON:

isi callback RISKEVENT (JSON asli, terverifikasi di emulator)
{
  "datatype": "riskevent",
  "key": "event_android_unofficial_installation_source", // jenis ancaman
  "name": "Unofficial Installation Source",              // nama singkat
  "desc": "Unofficial Installation Source",
  "riskLevel": "high",                                    // low | medium | high
  "responseType": 1,                                      // aksi RASP (int)
  "responseI18n": "[{\"language\":\"en_US\",\"alerttitle\":\"...\",\"alertmsg\":\"...\"}]",
  "eventId": "1141###<udid>###<start_id>###11###event_android_unofficial_installation_source",
  "time": 1789828899241
}
Diverifikasi end-to-end (emulator → collector → Wazuh)

Diuji nyata: app contoh Kotlin (SDK 5.14.0, app_id 1141) di Android emulator menangkap callback (callbacks:2, salah satunya milik aplikasi), mem-POST payload ke collector (HTTP 204), dan event muncul sebagai alert di Wazuh dengan level + MITRE yang benar, mis. event_enchanced_root → level 13 (T1548), event_high_risk_emulator_android → level 12 (T1497.001), event_risk_root → level 12. Nilai key callback sama persis dengan Security event pada metode S3, jadi rule SIEM yang sama langsung berlaku.

Field callbackArti
keyJenis ancaman, mis. event_risk_root, event_high_risk_MITM_android. Ini yang jadi security_event di SIEM.
name / descNama & deskripsi singkat ancaman.
riskLevellow / medium / high, pakai ini untuk memetakan severity di SIEM.
responseTypeKode aksi respons RASP (integer).
responseI18nTeks pesan respons (JSON per bahasa: alerttitle, alertmsg, buttonMsg).
eventIdID unik event (appId###udid###startId###seq###key), berguna untuk de-duplikasi.
timeWaktu event (epoch ms).

Callback kedua, Type.DEVINFO, memberi sidik jari perangkat (mis. udid). Simpan nilai terakhirnya, lalu gabungkan ke tiap event agar SIEM tahu perangkat mana.

Kabar baik

Sample resmi SecIron sudah menuliskan di komentar: "forward json to your backend REST API". Jadi meneruskan event ke collector memang alur yang diniatkan.

Bentuk Payload yang Dikirim ke SIEM

Agar bisa memakai rule SIEM yang sama dengan metode S3, kirim payload dengan skema yang seragam, gabungan event + device + user + konteks aplikasi + waktu:

payload yang dikirim app → collector
{
  "integration": "ironsky",
  "source": "sdk_callback",
  "ironsky": {
    "security_event": "event_risk_root",
    "risk_level": "high",
    "event_id": "1141###1a2b3c4d...###1789...###11###event_risk_root",
    "response_type": 1,
    "response_message": "Perangkat ter-root terdeteksi",
    "udid": "1a2b3c4d-0000-demo-udid-999999999999",
    "user_udid": "user-123",
    "app_id": "1141",
    "app_name": "Contoh Bank App",
    "os": "android",
    "os_version": "13",
    "model_name": "Pixel 8a",
    "event_time": "2026-09-19T12:00:00Z"
  }
}
Kenapa dibungkus ironsky?

Skema ini sama dengan hasil normalisasi pada metode S3, jadi decoder/rule SIEM (mis. yang mem-filter ironsky.security_event) langsung bisa dipakai ulang tanpa perubahan.

Langkah 1 — Bangun Payload di Callback

Di dalam callback RISKEVENT, ambil key/responseType, gabung dengan DEVINFO terakhir + userId + info app + timestamp, jadi satu objek seperti di atas. (Lihat kode lengkap per-framework di bawah.)

Jangan blok UI thread

Pengiriman jaringan harus di thread background (coroutine/AsyncTask/DispatchQueue), jangan di thread utama, supaya UI tidak nge-freeze saat event datang.

Langkah 2 — Kirim (POST) dari Aplikasi

Kirim payload sebagai JSON via HTTPS POST ke endpoint collector Anda, dengan header token autentikasi.

Kotlin — kirim dengan OkHttp (di background)
val body = payload.toString()
  .toRequestBody("application/json".toMediaType())
val req = Request.Builder()
  .url("https://collector.perusahaan-anda.com/ironsky")
  .header("Authorization", "Bearer <TOKEN_APP>")
  .post(body).build()
OkHttpClient().newCall(req).enqueue(object : Callback {
  override fun onFailure(call: Call, e: IOException) { /* simpan untuk retry */ }
  override fun onResponse(call: Call, resp: Response) { resp.close() }
})
Tangani offline

Jika POST gagal (tidak ada internet), simpan payload di antrean lokal dan coba lagi nanti. Atau andalkan metode S3 sebagai cadangan agar event tidak hilang.

Langkah 3 — Collector / Gateway

Collector adalah endpoint HTTPS kecil milik Anda yang: memeriksa token, (opsional) menormalkan, lalu menuliskan event ke tempat yang dibaca SIEM. Contoh minimal dengan Python Flask:

collector.py (contoh minimal)
from flask import Flask, request, abort
import json, os
app = Flask(__name__)
TOKEN = os.environ["APP_TOKEN"]           # token yang sama dgn di aplikasi
OUT   = "/opt/ironsky/out/events.jsonl"   # file yang dibaca SIEM

@app.post("/ironsky")
def ingest():
    if request.headers.get("Authorization") != f"Bearer {TOKEN}":
        abort(401)
    ev = request.get_json(force=True, silent=True) or {}
    with open(OUT, "a") as f:
        f.write(json.dumps(ev, ensure_ascii=False) + "\n")
    return ("", 204)
Wajib untuk produksi

Jalankan di belakang HTTPS/TLS (mis. Nginx + sertifikat), pakai token yang kuat, batasi rate (anti-spam), dan validasi payload. Collector ini contoh minimal, bukan siap-produksi apa adanya.

Langkah 4 — Collector → SIEM

Cara collector menyuapkan ke SIEM sama persis dengan sisi SIEM pada metode S3, tinggal pilih:

Opsi A — File yang di-tail SIEM (paling umum)

Collector menulis ke events.jsonl (seperti contoh di atas), lalu SIEM membacanya.

Wazuh — /var/ossec/etc/ossec.conf
<ossec_config>
  <localfile>
    <log_format>json</log_format>
    <location>/opt/ironsky/out/events.jsonl</location>
  </localfile>
</ossec_config>

Opsi B — Kirim langsung ke intake SIEM

Dari collector, teruskan ke input HTTP SIEM (mis. Splunk HEC, atau Elastic via pipeline). Untuk Splunk: POST https://splunk:8088/services/collector dengan header Authorization: Splunk <HEC_TOKEN>.

Ingat rotasi

Sama seperti metode S3, kalau memakai file events.jsonl, pasang logrotate dengan copytruncate agar disk tidak penuh.

Langkah 5 — Parsing & Deteksi

Karena payload memakai skema ironsky.* yang sama dengan metode S3, rule SIEM yang sama bisa dipakai ulang. Contoh rule Wazuh:

Wazuh — contoh rule
<group name="ironsky,seciron,">
  <rule id="100106" level="12">
    <decoded_as>json</decoded_as>
    <field name="ironsky.security_event" type="pcre2">^event_risk_root$</field>
    <description>IronSKY: rooted device ($(ironsky.udid))</description>
    <mitre><id>T1548</id></mitre>
    <group>rooting,</group>
  </rule>
</group>
Daftar lengkap event + level + MITRE

Gunakan tabel referensi security_event dari panduan S3 untuk membuat rule tiap jenis ancaman.

Kode per Framework

Tambahkan pengiriman ke collector di dalam callback RISKEVENT. Berikut inti kodenya per stack.

MainActivity.kt
RiskStubAPI.registerService(object : CallBack {
  override fun onResult(type: Type, result: Any) {
    val ev = result as? JSONObject ?: return
    val dev = DEVINFO   // JSONObject terakhir dari callback DEVINFO
    val payload = JSONObject().put("integration","ironsky").put("source","sdk_callback")
      .put("ironsky", JSONObject()
        .put("security_event", ev.optString("key"))
        .put("response_type", ev.optInt("responseType",-1))
        .put("udid", dev?.optString("udid"))
        .put("app_id", IronSkyConfig.APP_ID)
        .put("event_time", java.time.Instant.now().toString()))
    postToCollector(payload)   // OkHttp di background (lihat Langkah 2)
  }
}, Type.RISKEVENT, 0.5)

Verifikasi End-to-End

  1. Picu event di perangkat uji (mis. jalankan di emulator / device ter-root) → SDK memanggil callback.
  2. Cek collector menerima: lihat log collector, atau tail -f /opt/ironsky/out/events.jsonl.
  3. Cek SIEM: Wazuh → dashboard filter rule.groups: ironsky, atau alerts.json.
  4. Latensi: dari event muncul sampai tampil di SIEM harusnya beberapa detik.

Keamanan

  • Jangan taruh kredensial SIEM di aplikasi. Aplikasi hanya tahu URL collector + token app, bukan detail SIEM.
  • HTTPS + (opsional) certificate pinning dari app ke collector.
  • Token app yang kuat, dan idealnya bisa dirotasi/dicabut per rilis.
  • Rate limit & validasi di collector untuk mencegah penyalahgunaan endpoint.
Perhatian: app dilindungi RASP

Aplikasi yang memakai IronSKY biasanya juga menerapkan SSL pinning/anti-tamper. Pastikan koneksi ke collector Anda tidak ikut terblokir oleh kebijakan jaringan app.

Troubleshooting

GejalaPenyebab & Solusi
Callback tidak pernah terpanggilUrutan salah, registerService harus sebelum initAppsecEverisk (kritis di React Native).
POST gagal / timeoutCek URL collector, TLS/sertifikat, dan apakah kebijakan jaringan app memblokir domain collector.
Collector 401Token di app tidak sama dengan di collector.
Event masuk collector tapi tidak di SIEMPastikan SIEM membaca events.jsonl (log_format json) dan setiap baris JSON valid.
Event dobelRetry tanpa idempotensi. Sertakan id unik (mis. start_id+waktu) dan de-dup di collector.

FAQ

Apakah ini realtime?

Ya. Event dikirim saat terjadi (hitungan detik), berbeda dengan metode S3 yang batch harian.

Apakah harus mengubah aplikasi?

Ya, tapi hanya menambah beberapa baris di dalam callback RISKEVENT untuk mem-POST payload. SDK-nya sendiri sudah memanggil callback.
